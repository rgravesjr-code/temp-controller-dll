## 1. Decisions (owner + Scott, 2026-09-04)

| # | Topic | Decision |
|---|---|---|
| D1 | Structure | Two projects. **CanTp**: generic transport-protocol DLL/.so, no application logic. **TempCtl**: controller DLL/.so with no CAN and no hardware I/O, plus DBC generator and simulator app that uses CanTp. |
| D2 | Controller I/O | Pure signals in, signals out. Caller maps hardware. Minimum system = one temp input + heater/cooler outputs. |
| D3 | Deadband | Engineering units, **added to the setpoint**: `HiBand = Setpoint + DeadbandHi`, `LoBand = Setpoint − DeadbandLo`. |
| D4 | Relay feedback fault | Error is **set, operation continues** (not a stop). |
| D5 | Second temperature | Optional. Rationality check of Temp1 vs Temp2 with a tolerance for sensor location. With Temp2 enabled the controller **keeps running when one sensor fails** (out of Hi/Lo limits or bad reading), switching to the surviving sensor. Both failed → stop. No guarantee the final system has two sensors. |
| D6 | Averaging | Both temps averaged before the rationality compare, initially **4 points**. Reuse **ErrorTimeout** for feedback and rationality timers. |
| D7 | Database into the DLL | **Never load a DBC in the DLL** (RAM, performance). Two-call scheme: one call loads a message's scaling (start bit, length, factor, offset, type, min, max as 1-D arrays), another packs signal values. Multiple message definitions must coexist (temp controller + a simulated EC1, …). |
| D8 | Value type | Packer inputs are generic float (SGL, DBL variant too). The database scaling defines the wire type (e.g. a 5000 ms timeout passed as SGL, packed as U16). |
| D9 | DBC convention | Follow Vector's J1939 DBC: see EC1/RC in `J1939_NGHD_V130.dbc` (§3.4). |
| D10 | Linux test | A test setup that runs on 64-bit Linux (Raspberry Pi) is required, plus the cRIO check. Windows **and** Linux (Pi) versions of the simulator. |
| D11 | Order | CanTp first, then TempCtl v2 + DBC generator + simulator, then packages. |
| D12 | Transports in CanTp release 1 | Classic CAN, CAN FD single frame, J1939 BAM, plus receive (BAM reassembly + unpack). RTS/CTS and ISO-TP (handshake, session API) in release 2. Owner to confirm. |

## 2. Reference: how Vector defines a multipacket PG (EC1)

From `C:\CodeProjects\J1939ReferenceFiles\Conversion\J1939_NGHD_V130.dbc`:

```
BO_ 2566841342 EC1: 40 Vector__XXX
 SG_ EngineDefaultIdleTorqueLimit : 312|8@1+ (1,-125) [-125|125] "%" Vector__XXX
 SG_ EngDefaultTorqueLimit : 256|16@1+ (1,0) [0|64255] "Nm" Vector__XXX
 SG_ EngMomentOfInertia : 240|16@1+ (0.004,0) [0|257.02] "kg-m²" Vector__XXX
 ...
BA_DEF_ BO_ "VFrameFormat" ENUM "StandardCAN","ExtendedCAN","reserved","J1939PG";
BA_ "VFrameFormat" BO_ 2566841342 3;          <- J1939PG
BA_ "GenMsgSendType" BO_ 2566841342 8;
BA_ "SPN" SG_ <id> <signal> <spn>;
```

- ID `2566841342 = 0x98FEE3FE`: priority 6, PGN 0xFEE3 (65251), **SA 0xFE as
  a placeholder** ("any source"). The DBC ID has bit 31 set (extended flag in
  DBC convention) — mask with `0x1FFFFFFF`.
- Message length 40 bytes (> 8) + `VFrameFormat = J1939PG` ⇒ sent by J1939
  transport (BAM when broadcast). Lengths seen in the file: 9..40 here, up to
  1785 legal.
- Signals are plain Intel (`@1`) with start bits numbered linearly across the
  whole 40-byte payload (byte n, bit b → n·8 + b). Motorola (`@0`) start bits
  use the same sawtooth rule as in an 8-byte frame, just continuing.
- `SIG_VALTYPE_` marks IEEE float signals; not used by EC1.

CanTp's table format is a direct transcription of this: one message
definition = the `BO_` line + attributes, one signal row per `SG_`.

## 3. Project 1 — CanTp (new repo `can-tp-dll`)

### 3.1 Scope

Generic CAN transport-protocol packer/unpacker for LabVIEW CLFN and any
native caller. Library `cantp.dll` (x64, x86) and `libcantp.so` (x86_64 for
cRIO, aarch64 for Pi). Exports prefixed `CanTp_`. No application logic, no
hardware, no file I/O, no allocation after define (static slot tables).

### 3.2 Two-call API (draft, matches D7/D8)

```c
uint32_t CanTp_Version(void);

/* Load one message definition into a slot. Called once per message
 * (temp controller in slot 0, EC1 in slot 1, ...). */
int32_t CanTp_Define(int32_t slot,
                     const double* msgDef, int32_t msgDefLen,      /* CANTP_MSGDEF_COLS */
                     const double* sigDefs, int32_t nSig);         /* nSig x CANTP_SIGDEF_COLS */
int32_t CanTp_Clear(int32_t slot);
int32_t CanTp_SignalCount(int32_t slot);
int32_t CanTp_OutputSize(int32_t slot);      /* bytes of raw frames one Pack produces */

/* Pack physical values -> NI-XNET raw frame records (all frames of the
 * transport sequence). SGL and DBL flavours. */
int32_t CanTp_Pack(int32_t slot, const double* values, int32_t nValues,
                   uint64_t timestamp100ns, uint64_t spacing100ns,
                   uint8_t* out, int32_t outLen, int32_t* bytesWritten);
int32_t CanTp_PackSgl(int32_t slot, const float* values, int32_t nValues,
                      uint64_t timestamp100ns, uint64_t spacing100ns,
                      uint8_t* out, int32_t outLen, int32_t* bytesWritten);

/* Receive. Stateless over a buffer holding a whole sequence (sim, logs)... */
int32_t CanTp_Unpack(int32_t slot, const uint8_t* frames, int32_t framesLen,
                     double* values, int32_t nValues, int32_t* bytesConsumed);
/* ...and stateful one-frame-at-a-time for live buses; returns 1 when a
 * message completed and `values` is filled, 0 otherwise. */
int32_t CanTp_RxFeed(int32_t slot, const uint8_t* frame, int32_t frameLen,
                     double* values, int32_t nValues);
int32_t CanTp_RxReset(int32_t slot);

int32_t CanTp_NclHeader(uint8_t* out, int32_t outLen);            /* 12-byte .ncl header */
```

`msgDef` columns (DBL): 0 CAN ID as in the DBC (29-bit with priority/PGN/SA,
bit 31 ignored) · 1 extended (0/1) · 2 length in bytes (1..1785, or 9..64 for
CAN FD) · 3 transport (0 classic, 1 J1939 BAM, 2 CAN FD, 3 J1939 RTS/CTS
[rel 2], 4 ISO-TP [rel 2]) · 4 source address override (−1 = use ID's SA;
lets a 0xFE placeholder DBC be reused per node) · 5 destination address
(0xFF broadcast) · 6 pad byte (0xFF J1939, 0xCC/0xAA ISO-TP, 0 for classic
fill) · 7 cycle ms (informational, echoed by `CanTp_CycleMs`).

`sigDef` columns (DBL): 0 start bit (DBC numbering) · 1 bit length ·
2 byte order (0 Intel, 1 Motorola) · 3 value type (0 unsigned, 1 signed,
2 float32, 3 float64) · 4 factor · 5 offset · 6 min · 7 max. Same as v1.0
minus the frame-index column (one slot = one message).

Sizing: 32 slots × 128 signals × 8 doubles = 256 KB static; adjust if Scott
wants smaller. Values arrays are one physical value per signal row, in row
order. Values outside min/max are clamped; raw values are saturated to the
bit width; missing values (NaN) pack as the type's "not available" pattern
(all ones) — J1939 convention.

Output record format is unchanged from v1.0: 24-byte NI-XNET raw frame
record, extended to `24 + 8·ceil((len−8)/8)` bytes for CAN FD payloads
(PayloadLength byte + 8-byte units, exactly as the .ncl spec).

### 3.4 DBC conventions document (deliverable)

`docs/DBC-CONVENTIONS.md` in `can-tp-dll`, stating exactly:

1. One `BO_` = one CanTp message definition. `BO_` length ≤ 8 → classic
   frame; > 8 with `VFrameFormat = J1939PG` → J1939 BAM (rel 1) or RTS/CTS
   (rel 2, selected by destination ≠ 0xFF); > 8 with `VFrameFormat =
   ExtendedCAN`/`StandardCAN` and ≤ 64 → CAN FD; `CANFD_BRS`/`VFrameFormat`
   FD variants as Vector emits them. ISO-TP messages carry a custom
   attribute `TpProtocol = ISOTP` (rel 2).
2. ID: DBC 29-bit ID with bit 31 stripped; priority/PGN/SA decoded from it;
   SA 0xFE means "supplied at define time" (msgDef col 4).
3. Start bits: Intel linear across the payload; Motorola sawtooth continues
   across bytes (matches cantools/CANalyzer).
4. `SIG_VALTYPE_` 1/2 → float32/float64. Signed via `-`.
5. Attributes read by `dbc2tables`: `VFrameFormat`, `GenMsgCycleTime`,
   `GenMsgSendType`, `SPN` (informational, kept in the table comment column
   of the CSV/JSON only).
6. "Not available" packing rule and padding byte.

Plus `tools/dbc2tables.py`: `.dbc` → per-message tables as C header,
JSON (for the simulator) and CSV (for LabVIEW to read into a 2-D DBL), using
cantools as the parser. This is the only place a DBC is ever parsed.

## 4. Project 2 — TempCtl v2 (this repo)

### 4.1 Scope

Controller DLL/.so only (`tempctl.dll` / `libtempctl.so`, exports `Tc*`),
the throwaway DBC generator for the controller message, and the simulator.
All CAN code leaves this repo (→ CanTp). Version 2.0.0, breaking layout.

### 4.2 Controller behaviour v2

Inputs (SGL, every call): Setpoint, DeadbandHi, DeadbandLo (offsets, D3),
HiLimit, LoLimit, ErrorTimeoutMs, DeadbandTimeoutMs, FilterPoints (1..64,
default 4, D6), Temp1, Temp2, Temp2Enable, Temp2Tolerance, FeedbackEnable,
HeaterFeedback, CoolerFeedback, initial HeatingActive/CoolingActive (Init only).

Outputs (SGL): echo of all inputs, then HeatingCmd, CoolingCmd, ErrorStatus,
TempStatus, ControlTemp (filtered value driving control), Temp1Filtered,
Temp2Filtered, HiBand, LoBand (absolute, D3), ErrorRemainMs,
DeadbandRemainMs, ActiveSensor (1/2). About 29 values; exact indices fixed
in `tempctl.h` v2 and mirrored in the generated DBC.

Rules:

- Control loop as v1 (deadband countdown → relay, relay until setpoint,
  countdown starts at first observation, live config every call) but on
  `ControlTemp` = moving average (FilterPoints) of the active sensor.
- **Sensor rationality** (per sensor, each averaged): out of Hi/Lo limits or
  NaN/Inf for ErrorTimeout ⇒ that sensor is *failed* (latched until Reset).
  - Temp2Enable = 0: Temp1 failed ⇒ controller **stops** (relays off,
    latched), as v1.
  - Temp2Enable = 1: one sensor failed ⇒ **keep running on the other**,
    ActiveSensor switches, ErrorStatus bit set, TempStatus = degraded. Both
    failed ⇒ stop.
  - Disagreement |Temp1f − Temp2f| > Temp2Tolerance for ErrorTimeout ⇒
    ErrorStatus bit "sensors disagree", keep running on the active sensor
    (cannot tell which one is wrong from two readings). If one sensor later
    fails its limits, the failover rule above applies.
  - A sensor that returns inside its limits does not un-fail until Reset
    (avoids flapping); the owner may relax this.
- **Feedback** (FeedbackEnable = 1): after each Step the commanded relay
  state is remembered; next Step compares HeaterFeedback/CoolerFeedback
  with the previous command. Mismatch for ErrorTimeout ⇒ ErrorStatus bit
  (heater / cooler feedback), **operation continues** (D4). Bit clears when
  feedback matches again for ErrorTimeout? — open question Q2.
- **ErrorStatus** becomes a bit mask (fits a 16-bit CAN signal): b0 T1 hi,
  b1 T1 lo, b2 T1 bad, b3 T2 hi, b4 T2 lo, b5 T2 bad, b6 disagree, b7 heater
  feedback, b8 cooler feedback, b9 config warning. Scott's original 0/1/2
  enum is preserved as the low bits for a single-sensor system.
- **TempStatus** enum: 0 in band, 1 heat pending, 2 heating, 3 cool pending,
  4 cooling, 5 error pending, 6 stopped (fault), 7 degraded (running on
  backup sensor), 8 filter warm-up.
- Filter warm-up: until FilterPoints samples exist, average what is there;
  TempStatus 8 reports it; timers run normally.

### 4.3 DBC generator (throwaway)

`tools/make_tempctl_dbc.py`: emits `tempctl.dbc` (one `BO_`, PGN 65280
Proprietary B, priority 6, SA 0xFE placeholder, `VFrameFormat J1939PG`,
length ≈ 60 bytes with scaled integers: temps 16-bit 0.03125 °C −273
offset (J1939 SPN style), timeouts U16/U32 ms, flags 1–2 bits, status
enums 4/8 bits, bitmask 16 bits, ms countdowns U16) and, through CanTp's
`dbc2tables`, the tables the simulator and LabVIEW load. The signal order
in the DBC is the controller's output array order, so `CanTp_PackSgl(slot,
tcOut, n, …)` needs no reordering.

### 4.4 Simulator

- `sim/TempSim.Core` (.NET 10 class library): plant model (ambient lag +
  heater/cooler rates), sensor models (offset, noise, stuck, open), relay
  feedback model (with a "stuck relay" switch), P/Invoke to `tempctl` and
  `cantp`, pack → raw records → unpack round trip, JSON config, CSV/.ncl
  logging. No UI dependencies.
- `sim/TempSim.Wpf` (Windows): graph (limits, band edges, setpoint, Temp1,
  Temp2, ControlTemp), countdown displays, relay lamps, feedback toggles,
  heating/cooling rate settings, temperature override slider, settings
  persisted, frames panel (hex records) beside decoded values.
- `sim/TempSim.Cli` (cross-platform console): same core, scripted scenarios
  (warm-up, setpoint step, sensor failure with failover, feedback fault),
  prints a state table and writes the CSV/.ncl; published self-contained
  for `linux-arm64` (Pi) and `linux-x64`. Identical CSV on Windows and Pi
  is the cross-platform proof. Optionally puts the frames on the Pi's real
  CAN bus via SocketCAN.
